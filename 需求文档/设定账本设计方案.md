# 设定账本（Canon Ledger）设计方案

> 状态：**设计稿，待评审后再实现**
> 目标：解决长篇（100 章以上）AI「吃书」——人物称呼、能力境界、物品来历、位置、时间线、伏笔前后不一致。

---

## 1. 问题定位

当前记忆链路是**三次有损压缩**：

```
章节原文 → 章节摘要（chapter_summaries） → 每 10 章分组摘要（story_memory_groups） → Story Bible（story_memory）
```

压缩只保留「剧情主干」，以下事实基本必然丢失：

- 同一角色的多种称呼（林动 / 小动 / 林兄）
- 状态类事实（左臂受伤、境界、欠谁人情、身怀何物）
- 物品来历、首次出现章节
- 精确时间线与因果关系
- 已埋未收的伏笔

**结论：把「记忆」从「摘要」改成「账本」。摘要只做导航，结构化事实才是真相源。**

---

## 2. 数据模型（新增表，全部迁移式增量，不动现有表）

```sql
-- 实体：角色 / 地点 / 势力 / 物品 / 功法 / 术语
CREATE TABLE IF NOT EXISTS canon_entities (
    id            TEXT PRIMARY KEY,          -- canon_<uuid>
    book_id       TEXT NOT NULL,
    kind          TEXT NOT NULL,             -- character | location | faction | item | skill | term
    name          TEXT NOT NULL,             -- 规范名
    summary       TEXT NOT NULL DEFAULT '',  -- 100~200 字稳定特征
    attrs         TEXT NOT NULL DEFAULT '{}',-- JSON：身份/外貌/能力/持有物/关系
    first_chapter INTEGER,                   -- 首次出现章序号
    last_chapter  INTEGER,                   -- 最近出现章序号
    status        TEXT NOT NULL DEFAULT 'active', -- active | dead | missing | sealed
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    UNIQUE(book_id, kind, name)
);
CREATE INDEX IF NOT EXISTS idx_canon_entities_book ON canon_entities(book_id, kind);

-- 别名（归一化后的小写形式做索引）
CREATE TABLE IF NOT EXISTS canon_aliases (
    book_id   TEXT NOT NULL,
    alias     TEXT NOT NULL,                 -- 原文别名
    alias_key TEXT NOT NULL,                 -- 归一化（小写/去空格）
    entity_id TEXT NOT NULL,
    PRIMARY KEY (book_id, alias_key),
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (entity_id) REFERENCES canon_entities(id) ON DELETE CASCADE
);

-- 状态随时间变化：查询某章时取 seq <= 目标章的最后一条
CREATE TABLE IF NOT EXISTS canon_states (
    id         TEXT PRIMARY KEY,
    book_id    TEXT NOT NULL,
    entity_id  TEXT NOT NULL,
    chapter_id TEXT NOT NULL,
    seq        INTEGER NOT NULL,             -- 全书递增，保证顺序
    field      TEXT NOT NULL,                -- 境界/位置/伤势/持有物/关系…
    value      TEXT NOT NULL,
    quote      TEXT NOT NULL DEFAULT '',     -- 原文依据，便于核对
    created_at INTEGER NOT NULL,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (entity_id) REFERENCES canon_entities(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_canon_states_lookup ON canon_states(book_id, entity_id, seq);

-- 事件流：只追加，永不压缩
CREATE TABLE IF NOT EXISTS canon_events (
    id          TEXT PRIMARY KEY,
    book_id     TEXT NOT NULL,
    chapter_id  TEXT NOT NULL,
    seq         INTEGER NOT NULL,
    subject_id  TEXT,                        -- 可空：环境/群体事件
    predicate   TEXT NOT NULL,
    object      TEXT NOT NULL DEFAULT '',
    quote       TEXT NOT NULL DEFAULT '',
    importance  TEXT NOT NULL DEFAULT 'normal', -- high | normal
    created_at  INTEGER NOT NULL,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_canon_events_book ON canon_events(book_id, seq);

-- 硬设定（不可违反）
CREATE TABLE IF NOT EXISTS canon_rules (
    id         TEXT PRIMARY KEY,
    book_id    TEXT NOT NULL,
    rule       TEXT NOT NULL,
    quote      TEXT NOT NULL DEFAULT '',
    chapter_id TEXT,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE
);
```

说明：

- `canon_states` 用「追加 + 按章取最后一条」的方式表达状态变化，避免覆盖历史。
- `seq` 用 `MAX(seq)+1` 在写入时分配（单写入者：后台抽取任务串行化 per book）。
- 所有实体/事件都带 `quote`，冲突时可以指回原文，方便用户判断。
- 别名表与现有 `character_cards.aliases` 不冲突：角色卡是「人写的」，账本是「抽出来的」，实现时二者合并查询，冲突以角色卡为准。

## 3. 每章增量抽取（核心流程）

**触发**：章节摘要生成成功后（`summary_generator_service::generate_chapter_summary_with_lock` 返回 Ok 时），异步 spawn 一次抽取。只处理本章，不重扫全书。

**输入**：本章标题 + 正文（截断到 8k 字）+ 现有相关实体卡（用本章标题/正文做朴素匹配命中的实体）。

**输出**（`prompts/agents/canon_extract.md` 约束为严格 JSON）：

```json
{
  "entities": [
    { "kind": "character", "name": "林动", "aliases": ["小动", "林兄"],
      "summary": "……", "attrs": { "身份": "…", "能力": "…" } }
  ],
  "states": [
    { "entity": "林动", "field": "境界", "value": "筑基三层", "quote": "原文依据" }
  ],
  "events": [
    { "subject": "林动", "predicate": "击败", "object": "王虎",
      "quote": "…", "importance": "high" }
  ],
  "threads": { "add": ["…"], "resolve": ["…"] },
  "rules": [ { "rule": "…", "quote": "…" } ]
}
```

**落库规则**：

1. 实体按 `(book_id, kind, name)` upsert；别名写 `canon_aliases`，遇到「别名已属于另一个实体」→ 记一条冲突待确认。
2. `states` 追加，但如果同一实体同一字段在本章内出现多次，只留最后一条。
3. `events` 追加。
4. `threads.add` 追加到该书未解决列表；`threads.resolve` 标记解决（软删除或状态位）。
5. **高风险变更**（`status` 改为 dead、关系反转、能力大幅升降）不自动生效，写进 `detected_conflicts` 让用户在冲突面板确认。
6. 抽取失败只记日志，不阻塞摘要/写作。

**成本控制**：用便宜模型；输入截断；只对「新增/修改过的章节」抽取；同一章重复触发用现有 `GENERATING_CHAPTERS` 类似的集合去重。

## 4. 工具接口（给决策 AI）

| 工具 | 参数 | 返回 | 用途 |
|---|---|---|---|
| `resolve_entity` | `name` | `{entityId, 规范名, kind, 别名[], 首次/最近出场章}` | 别名归一，先解析再查 |
| `get_canon` | `entityIds[]`, `asOfChapter?` | 实体卡数组（含截至该章的状态 + 最近 5 条事件） | 写作/回答设定问题的主力 |
| `search_canon` | `query`, `kind?` | 匹配的实体/规则列表（含 ID） | 模糊找设定 |
| `get_timeline` | `subject`, `fromChapter?`, `toChapter?` | 事件序列 | 核对时间线 |

`get_canon` 返回格式（每实体约 150–300 token）：

```
【角色】林动（别名：小动、林兄）  首次：第 1 章  最近：第 87 章
身份：青阳城林家族人 → 内门弟子
当前状态（截至第 87 章）：境界 筑基三层；左臂轻伤；持「雷帝印」
关系：师父 柳擎；对手 王虎
相关伏笔：雷帝印的来历未解
最近事件：
- 第 85 章 击败王虎（影响：声名鹊起）
- 第 87 章 进入雷池（影响：…）
```

`search_chapter_content` 保留，作为「原文级」兜底；两者分工：**先 canon 定位，再原文求证**。

## 5. 写作上下文组装（Canon Pack）

`write_chapter` 触发前，自动拼装：

```
[本章粗纲/细纲]
[出场实体卡]        ← 用大纲 + 用户指令里的名字/别名匹配，取 5~12 张
[这些实体在上一章的末态]
[相关未解决伏笔 top5]
[最近 1~2 章结尾原文 500~800 字]
[硬设定规则]
```

要点：

- **确定性组装**，不依赖决策 AI 这一轮碰巧查到什么。
- 匹配不到实体时明确写「未收录」，并提示决策 AI 用 `ask_user` 或先 `search_chapter_content`。
- 预算：整个 pack 控制在 6k token 内；实体卡按「本章出现次数」排序截断。

---

## 6. 写前锁定 + 写后自检

- **写前**：决策 AI 输出 3–5 条「本章必须遵守」（人物状态、称呼、地点、时间、规则），拼进 writer prompt。
- **写后**：只针对「本章出现的实体 + 本章新增事实」做一次轻量校验：
  - 已死角色出场
  - 状态倒退（对照 `canon_states`）
  - 别名混用到两个人
  - 违反 `canon_rules`
  - 新事实未登记
- 校验结果展示在正文卡片上，**不阻塞插入**，但需用户确认一次；确认后把新事实写回账本。

---

## 7. 兼容与迁移

- 新增表全部 `CREATE TABLE IF NOT EXISTS`，不改现有表结构。
- 角色卡（`character_cards`）继续可用：查询时先查角色卡，再查 `canon_entities`，同名以角色卡为准并可把角色卡字段回填到账本。
- 已有书支持「重建账本」：后台按章顺序跑抽取（可复用故事记忆的进度 UI），完成后 `story_memory` 仍保留作为导航目录。
- `story_memory` 不再作为唯一事实来源，只保留「总览 + 分卷梗概」用于快速浏览。

## 8. 实施拆分

| 阶段 | 内容 | 预估 |
|---|---|---|
| P1 | 建表 + `canon_service` 基础读写 + 单章抽取（只抽角色/地点/物品/状态） | 1–1.5 天 |
| P2 | 4 个查询工具 + 写作前 canon pack 组装 | 1 天 |
| P3 | 写后自检 + 冲突面板接入 + 高风险变更确认 | 1 天 |
| P4 | 已有书批量重建 + 进度 UI + 手工编辑实体 | 1 天 |

验收标准（用一本 ≥100 章的书）：

1. 任取 10 个角色，`get_canon` 能返回正确的别名、首次出场章、当前状态。
2. 写新章时，写作 AI 的上下文中包含本章出场角色的 canon 卡。
3. 人为制造「已死角色说话」「境界倒退」「称呼错人」，写后自检能报出。
4. 100 章书的一次普通对话，system prompt 体积相比现在下降 ≥50%。

---

## 9. 风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| 抽取成本 | 每章一次 LLM 调用 | 便宜模型 + 输入截断 + 只处理变更章 |
| 抽取错误 | AI 把路人甲抽成主角 | 带 `quote`、低置信度不落库、用户可编辑 |
| 过度设计 | 一上来做向量库/图数据库 | 先做结构化 + 别名 + 关键词检索，够用再上向量 |
| 别名歧义 | 同一称呼指两个人 | 冲突表 + 用户确认，不自动合并 |
| 状态爆炸 | 每章都记状态 | 只在字段变化时追加 |

---

## 10. 与现有方案的对比

| 现有 | 问题 | 本方案 |
|---|---|---|
| Story Bible 一次性大总结 | 三次有损压缩 | 增量账本；摘要只做导航 |
| 关键词 `contains` | 别名/近义召回差 | 别名展开 + 排序 + 片段（已实现基础版） |
| 更新时全书重扫 | token 爆炸、丢细节 | 每章只处理本章 |
| 写作上下文靠现查 | 漏查就吃书 | 自动 canon pack 兜底 |
| 冲突检测异步、报在侧栏 | 发现太晚 | 写后本章自检 + 插入前确认 |
